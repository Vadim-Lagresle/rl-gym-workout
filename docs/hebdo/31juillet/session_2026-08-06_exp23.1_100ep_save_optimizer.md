## 3. Le code : `--save-best-optimizer`

Deux fichiers touchés, changement minimal :

- `src/train/train_grpo.py` : nouveau flag `--save-best-optimizer`, transmis à
  `TestEvalCallback` (ligne ~593).
- `src/train/periodic_eval.py` (`TestEvalCallback.on_step_end`) : quand un
  nouveau best test arrive,
  1. l'ancien `optimizer.pt` du best courant est supprimé **avant** d'écrire le
     nouveau modèle — ça plafonne le pic disque à ancien modèle + nouveau modèle
     (~17.8 Go max) au lieu d'y ajouter les 6.2 Go de l'ancien optimiseur ;
  2. le modèle est swappé atomiquement comme avant (`.tmp` → `os.replace`) ;
  3. le nouvel `optimizer.pt` est écrit **après** le swap, lui-même en
     `.tmp` + `os.replace` — un fichier présent est toujours complet ;
  4. un échec de l'écriture optimiseur ne perd ni le best (déjà swappé) ni le
     run (try/except dédié, message `!!! SAUVEGARDE OPTIMIZER ÉCHOUÉE`).

  Fenêtre de risque assumée : si le pod meurt entre (1) et (3), le best a ses
  poids mais pas d'optimiseur — jamais pire que le comportement historique.

Validation à sec (`/tmp/test_optsave.py`, env v2, sans GPU) : éval monkeypatchée,
4 cas passés — écriture initiale, remplacement au 2e best, échec simulé (« disque
plein ») sans casse, et flag off = comportement historique strictement inchangé.
