## Point de vigilance — uuid et groupement GRPO

Dans verl (`ray_trainer.py` L.796) :
```python
batch.non_tensor_batch['uid'] = np.array([str(uuid.uuid4()) for _ in range(len(batch))])
batch = batch.repeat(repeat_times=N, interleave=True)
```
Chaque item reçoit un `uid` unique **avant** d'être répété N fois. Les N trajectoires
du même item partagent donc le même `uid`. Dans `compute_grpo_outcome_advantage`,
ce `uid` sert à regrouper les N scores pour calculer mean/std par groupe.

**Risque dans notre stack TRL** : si TRL ne groupe pas correctement les N=8
trajectoires par item pour la normalisation de l'avantage, le mean/std est calculé
sur l'ensemble du batch (64 trajectoires) plutôt que par groupe de 8. Ça donne des
avantages mal calibrés → signal GRPO faussé. À vérifier dans le code TRL.

## Libs notées

**OmegaConf** (`omegaconf`) — lib de gestion de configs hiérarchiques en YAML.
Accès en pointillé (`config.trainer.lr`), interpolation (`${trainer.lr}`),
merge de configs. C'est la couche "objet config" utilisée par Hydra et verl.

**codetiming** — chronomètre léger par section de code. Dans verl, mesure
`timing_s/gen`, `timing_s/update_actor` etc. à chaque step.
Intéressant à ajouter dans notre callback `_MemDiagCB` pour décomposer
rollout vs optimizer step (actuellement on a seulement `step_time` global).
À considérer si on veut diagnostiquer des ralentissements par phase.

**`with` / contextmanager** — `with` garantit qu'un code de nettoyage s'exécute
toujours à la fin d'un bloc, même si une exception est levée (ex: fermer un fichier,
enregistrer un temps). `@contextmanager` permet de créer son propre `with` avec une
fonction simple : tout ce qui est avant le `yield` s'exécute à l'entrée du bloc,
tout ce qui est après s'exécute à la sortie. Dans verl : utilisé pour mesurer le
temps de chaque phase (`gen`, `update_actor`…) sans polluer le code de `fit()`.

**ABC** (`from abc import ABC, abstractmethod`) — système de classes abstraites Python.
Permet de définir un "contrat" : toute sous-classe doit implémenter les méthodes
marquées `@abstractmethod`, sinon Python lève une erreur au démarrage.
Dans verl : `RoundsScheduler` est abstraite, `FixedRoundsScheduler` et
`StepRoundsScheduler` sont les implémentations concrètes. Garde-fou architecturale —
si on ajoute un nouveau scheduler sans implémenter `get_rounds()`, Python crie
immédiatement plutôt qu'en plein milieu d'un entraînement.
