# Semaine du 10 juillet — Runs exp10.5 → exp10.7 (série warm-start LoRA)

Rapport de traçabilité des trois derniers runs de la série **exp10** (GRPO LoRA
sur Qwen2.5-3B, TextCraft, B200). Objectif de la série : partir d'un checkpoint
déjà entraîné et **pousser le pass@1 le plus haut possible en LoRA pur**, en
jouant surtout sur le learning rate et sur le point de départ (warm-start).

Ces runs prolongent exp10.3 (checkpoint fusionné à 35/100). Le fil rouge :
chaque run produit un best, qu'on **fusionne** (base + adapter → modèle complet)
pour servir de point de départ au suivant.

---

## 1. Hyperparamètres — ce qui est COMMUN aux 3 runs

Tout est identique d'un run à l'autre **sauf le learning rate et le modèle de
départ**. À garder en tête pour comparer proprement.

| Paramètre | Valeur | Où |

| LoRA — `lora_dropout` | 0.0 | `train_grpo.py:972` |
| LoRA — `bias` | none | `train_grpo.py:973` |
| LoRA — `target_modules` | **les 7** : `q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj` | `train_grpo.py:975` |
| Optimizer | `adamw_torch` | (LoRA → pas besoin du 8-bit) |
| **KL — `beta`** | **0.01** | `--beta 0.01` |
| `num_generations` (N) | 8 | groupe GRPO |
| `gradient_accumulation_steps` | 64 | → 8 prompts × 8 gens = **64 trajectoires/step** |
| `max_completion_length` | 512 (par tour) | |
| `max_rounds` (tours/épisode) | 20 | |
| Reward | sparse outcome 0/1 (succès craft final) | |
| Éval | pass@1 sur 100 items, tous les 23 steps | `--eval-every 23 --eval-items 100` |
| Sauvegarde | `--save-best-only` → **adapter PEFT seul** (~qq dizaines de Mo) | fix disque exp10.3 |

> **Note sur le KL** : `beta=0.01` ici est **10× plus élevé** que la recette
> papier (`1e-3`). C'est un choix de la série exp10 pour brider la dérive de la
> policy en LoRA. En pratique le KL mesuré reste très bas en début de run (~0)
> puis monte quand le run commence à diverger (cf. collapse §5).

> **Note sur LoRA `r=16`** : rang volontairement modeste. α=32 donne un facteur
> d'échelle α/r = 2 sur les deltas. Les 7 modules (attention *et* MLP) sont
> ciblés → adapter « large mais peu profond ». Ce rang n'a **pas** été varié dans
> la série (candidat d'ablation futur si on veut plus de capacité).

> **step_time** : ~20 s/step au début, mais **jusqu'à ~232 s/step en fin de run**.
> Ce ×10 n'est pas un ralentissement matériel : c'est le collapse (§5) qui fait
> exploser la longueur des completions (donc le temps de génération). Les ~18 h
> sont donc gonflées par la phase divergente — un run sain de 530 steps prendrait
> plutôt ~3 h.

**Courbe pass@1** (éval /100, tous les 23 steps) :

```
step:  23  46  69  92 115 138 161 184 207 230 253 276 299 322 345 368 391 414 437 460 483 506
pass:  31  30  33  37  34  32  38  43  37  42  31  40  40  45  43 [51] 43  33  22   9  12   3
                                                              ^BEST        └──── collapse ────┘
```

**Lecture** : montée lente mais réelle jusqu'à **51/100 au step 368** — record
TRL du projet à ce moment (vs 38 verl exp6). Puis **collapse net** après ~step
400 : les completions dégénèrent (longueur moyenne 250 → 6500 tokens), le KL
passe de 0 à 0.2–0.3, les `invalid_steps` saturent (≈20/20), l'éval s'effondre
51 → 3. L'éval finit même par crasher au step 529 (`prompt 16398 > max_model_len
16384`). Run coupé vers step 530/600.

## 5. Le pattern « collapse » de la série

Sur les runs longs (10.5 surtout), on observe systématiquement la même
dégradation passé un certain nombre de steps :

1. Les completions s'allongent anormalement (250 → plusieurs milliers de tokens).
2. Le KL décolle (0 → 0.2–0.3) : la policy s'éloigne franchement de la référence.
3. Les `invalid_steps` saturent : le modèle génère des actions mal formées.
4. Le pass@1 s'effondre, jusqu'à faire crasher l'éval (prompt > `max_model_len`).

C'est **la** motivation de la stratégie warm-start + baisse de LR : au lieu de
laisser un run long diverger, on prend son meilleur point, on le fige (merge) et
on repart avec un LR plus doux. D'où la suite ci-dessous.

## 6. Lignée des modèles & suite (exp10.8, en cours)

```
exp10.3 (35 %)
   │  LoRA, LR 3.333e-6 (÷1.5)
   ▼
exp10.5  best 51 %  ──merge──▶  qwen25_3b_exp10p5_step368_51pct
   │  warm-start LoRA, LR 2.2e-6
   ▼
exp10.7  best 53 %  ──merge──▶  qwen25_3b_exp10p7_step92_53pct
   │  warm-start LoRA, LR 7.333e-7 (÷3)
   ▼
exp10.8  ◀── EN COURS (lancé 2026-07-07, wandb bfkkqcaj, max_steps 400)

(exp10.6 : branche morte, abandonnée à 35 %)
```

**exp10.8** reprend donc exp10.7 depuis son best (53 %) avec le **LR encore divisé
par 3** (2.2e-6 → **7.333e-7**), tous les autres hyperparamètres identiques
(LoRA r=16/α=32, KL beta=0.01, N=8, batch 64). Hypothèse : un LR très doux depuis
un point déjà haut grappille quelques points sans re-déclencher le collapse.
Config : `runs/exp10.8_warmstart53_lr_div3/config.yaml`.
