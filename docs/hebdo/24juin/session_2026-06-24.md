- Log : `logs/exp16_qwen35_4b.log`

### Paradoxe oracle < multi-tour (Qwen3.5)

| Protocole | Pass@1 |
|---|---:|
| Exp 16b oracle single-turn | **54 / 100** |
| Exp 15 multi-tour interactif | **77 / 100** |
| Écart | **−23 pts** |

Intuition naïve : l'oracle (plan complet + exécution déterministe) devrait
*dominer* le multi-tour. Ce n'est pas le cas — et ce n'est **pas** un artefact
de limite de contexte : Exp 15 tourne en moyenne **13.9 tours** (max 30), largement
dans la fenêtre.

**Lecture** : sans contrainte mémoire, le **multi-tour interactif est plus facile**
que le one-shot oracle sur TextCraft, parce que :

- le feedback env (inventaire, échecs de `get`, recettes visibles à chaque tour)
  permet de corriger le raisonnement transitif en cours de route ;
- l'oracle exige un plan *et* une extraction JSON parfaits *sans* observation
  intermédiaire (deux LLM calls, zéro recovery) ;
- Qwen3.5 tire davantage profit du feedback iteratif (+23 pts multitour vs oracle)
  que Qwen2.5 (oracle 20 ≈ baseline multitour 18).

Implication RL : optimiser le contrôle multi-tour n'est pas « plus dur » que
planifier en one-shot ; au contraire, l'interaction env compense les lacunes de
raisonnement. Le goulot sur Qwen2.5 reste plutôt la *capacité de base* ; sur
Qwen3.5, c'est surtout l'*absence de feedback* qui plafonne l'oracle.
