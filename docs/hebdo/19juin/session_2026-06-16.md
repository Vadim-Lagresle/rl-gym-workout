## 1. Bug de sync vLLM — trouvé et corrigé (cause racine de runs invalides)

`_sync_trl_to_vllm` (train_grpo.py) recopiait les fichiers tokenizer **depuis le dossier
du moteur vLLM courant**. Après le 1ᵉʳ sync, ce dossier EST `/tmp/vllm_weight_sync` →
copie d'un fichier sur lui-même → `SameFileError` → avalée par le `try/except` → le
rechargement vLLM était **silencieusement abandonné**.

**Conséquence** : le générateur vLLM restait figé sur les **poids du step 1** pendant tout
le run. Fatal pour GRPO (on-policy) : les trajectoires venaient d'une policy gelée, la
courbe `reward` de wandb mesurait un modèle qui n'évoluait pas → plate par construction.
Bug **préexistant** : il plombait exp7.2 et le début d'exp7.3.

**Fix** : mémoriser le dossier du modèle d'origine dans `VLLM_BASE_MODEL_DIR` au 1ᵉʳ
chargement, et toujours copier les tokenizers depuis là. Vérifié : `vLLM rechargé avec les
poids du step N` apparaît désormais à **chaque** step (avant : seulement au step 1).

`src/eval/eval_oracle.py` : N=20 trajectoires/item (T=1.0, batché vLLM), pass@k non biaisé

**Analyse détaillée : `runs/oracle_best32/ANALYSIS.md`** + 3 figures dans le même dossier :
`passk_curves.png` (courbes pass@k par depth), `passk_histograms.png` (pass@1/10/20 base vs best),
`distribution_curves.png` (distribution réussites/item sur 20, brut + **KDE** lissé).

**pass@k par depth (base @1→@20 vs best @1→@20) :**
| depth | base | best |
|---|---|---|
| 1 | 27→94 | 79→100 |
| 2 | 4→44 | 18→**78** |
| 3 | 0→**0** | 1→**8** |
| 4 | 0→**0** | 0→**0** |
| global | 10→47 | 32→**65** |

**Verdict** (répond à la question centrale depth 3-4) :
- **Depth 2 = fiabilité** : marge RL **+60 pts** (sait 78%, fiable à 18%) → terrain du RL, priorité.
- **Depth 3-4 = capacité** : best plafonne 8% / 0% ; baseline **0 partout** (0/500, 0/60).
  pass@k=0 ⇒ pas de graine pour GRPO (**Dr. GRPO**) ⇒ RL pur insuffisant → **curriculum / SFT / CoT**.
- Nuance : le RL a **déplacé la frontière** (depth-2 +14 items atteignables, depth-3 +2 items
  jamais résolus par la baseline) → depth 3 est à la limite, pas un mur infini.

**Forme de la marge (distribution des réussites/20 par item, cf. `distribution_curves.png`)** :
distribution **bimodale** (pic à 0 = jamais, pic à 20 = toujours). Le RL décale la masse de 0
vers la droite. Le panier clé pour le RL = items résolus **1-5 fois/20** (« sait mais rare ») :
depth-2 best en a **21** → grosse réserve amplifiable ; depth-3 n'en a que **2** ; depth-4 **0**.
Confirme visuellement : marge RL = depth 2, mur de capacité = depth 3-4.

## 8. Diagnostic pass@k par depth dans eval_vllm.py (outillage curriculum)

Ajout d'un mode **diagnostic pass@k par profondeur** à `src/eval/eval_vllm.py`, sans
toucher au chemin pass@1 (qui reste la métrique principale, inchangée).

- **But scientifique** : avant d'investir dans un curriculum (depth 1→2→3→4), vérifier
  empiriquement si depth 3-4 est encore *atteignable* par échantillonnage. Si le modèle
  n'échantillonne jamais une trajectoire correcte (pass@k = 0), le RL n'a **aucune graine
  à amplifier** (cf. Dr. GRPO, arXiv:2503.20783 : pas de trajectoire correcte → reward
  uniforme → gradient nul). Lecture du curriculum : pass@k(depth4) qui monte 0→>0 au fil
  des paliers = pari compositionnel gagnant ; reste collé à 0 = rupture qualitative.
- **Implémentation** : nouvelles fonctions `load_depth_map` (réutilise
  `data/eval/textcraft_test_with_depth.json`), `run_pass_at_k_by_depth`, `write_passk_log`,
  `report_pass_at_k`. Flag `--passk K` (défaut 0 = off) lance le diagnostic **à la place**
  du pass@1 ; logs séparés dans `runs/<run>/eval_logs_passk/`. Seule modif d'une fonction
  existante : `run_episode` reçoit `temperature=1.0` (rétro-compatible, défaut = valeur
  actuelle) — nécessaire car les k échantillons d'un même item ne diffèrent qu'avec T>0.
- **Deux métriques reportées par depth, à NE PAS confondre** :
  - `pass@k` = fraction d'items résolus ≥1 fois sur k → **binaire par item**, donc sur les
    **3 items depth-4** la moyenne ne prend que {0, 0.33, 0.67, 1.0}. Lecture qualitative.
  - `succ/sample` = succès / (items × k) → sur depth-4 c'est **24 essais**, granularité fine.
    **C'est la colonne à privilégier pour depth 4** (peu d'items). depth 3 = 25 items, ok.
- **Distribution du test set** : depth1=31, depth2=41, depth3=25, **depth4=3** items.
- **Coût** : depths (3,4) × k=8 = (25+3)×8 = **224 rollouts** (~30-50 min). Poste lourd.
- **Validé à sec uniquement** : `py_compile` OK, `--help` OK, logique d'agrégation testée
  sur résultats factices (ratios corrects). ⚠️ **Smoke test GPU obligatoire avant le run
  complet** : la chaîne réelle (reset env + 8 rollouts/item via serveur vLLM) n'a PAS encore
  tourné. Test minimal recommandé : `--passk 2 --passk-depths 4` (3 items × 2 = 6 rollouts,
  ~1-2 min) sur la baseline, les deux serveurs (vLLM + textcraft) up.

## 9. Audit des 2 biais Dr. GRPO (arXiv:2503.20783) sur nos implémentations

Vérification de la conformité de notre TRL et du verl AgentGym (`external/`) aux deux
biais identifiés par Dr. GRPO : biais de longueur (÷ longueur de réponse) et biais de
difficulté (÷ écart-type du groupe). **Inspection seule, aucune modif de code.**

| | Biais de longueur | Biais de difficulté (÷ std) |
|---|---|---|
| Dr. GRPO préconise | ÷ constante `MAX_TOKENS` | **pas** de ÷ std |
| Notre TRL (`loss_type="dapo"`, `scale_rewards` défaut=`group`) | ÷ `num_items_in_batch` (tokens du batch) → **pas de biais par-réponse** | **÷ std** → biais présent |
| verl AgentGym (`masked_mean(axis=None)` ; advantage `/std`) | ÷ total tokens micro-batch → **pas de biais par-réponse** | **÷ std** → biais présent |

**Preuves :**
- TRL : `train_grpo.py:733` → `loss_type="dapo"` ⇒ `loss = (per_token_loss*mask).sum() /
  num_items_in_batch` (grpo_trainer.py:2580, TRL 1.4.0) = normalisation par-token sur le
  batch. `scale_rewards` non positionné ⇒ défaut `"group"` ⇒ `advantages /= (std+1e-4)`
  (grpo_trainer.py:2167-2168).
- verl : `core_algos.py:153` `(scores-mean)/(std+eps)` (le `unsqueeze` ligne 154 ne fait
  que diffuser le scalaire) ; `compute_policy_loss` (:305) `masked_mean(..., axis=None)` =
  `sum/total_tokens` (torch_functional.py:118-120).

**Conclusions :**
1. **Biais de longueur** : NI notre TRL NI le verl du papier n'ont le biais *fort*
   (par-réponse). Les deux normalisent par token sur le batch. Écart avec Dr. GRPO réduit à
   « total tokens batch » vs « constante MAX_TOKENS » → d'après l'article, n'affecte que
   l'échelle du gradient, pas la direction du biais. **Mineur.** Le choix `dapo` (vs le
   défaut `grpo`, lui biaisé car normalise par-réponse) était délibéré pour matcher verl.
2. **Biais de difficulté (÷ std)** : **les deux dévient de Dr. GRPO** — y compris le verl
   AgentGym qu'on réplique. Notre TRL réplique fidèlement verl (même `/std`). Donc pour
   **répliquer verl** on est aligné ✅ ; pour **tester Dr. GRPO pur** il faudrait
   `scale_rewards="none"` (et éventuellement `loss_type="dr_grpo"` pour le ÷ constante).
3. **Piste d'ablation** : `scale_rewards="none"` est un test Dr. GRPO **à un paramètre**,
   peu risqué — candidat propre une fois l'écart verl objectivé. À ne PAS confondre avec la
   réplication verl en cours (qui, elle, garde le `/std`).
