## Architecture (rappel)

Deux process indépendants, parlent en HTTP :

```
┌───────────────────────────┐  HTTP  ┌──────────────────────────┐
│  Trainer / Eval client    │  ───▶  │  Env server               │
│  (env conda agentgym-rl)  │        │  (env conda               │
│  vLLM + agentenv          │  ◀───  │   agentenv-textcraft)     │
│  GPU                      │        │  FastAPI + uvicorn        │
│                           │        │  port 36005               │
└───────────────────────────┘        └──────────────────────────┘
```

Endpoints REST exposés par chaque env-server :
`POST /create`, `POST /reset`, `POST /step`, `GET /observation`, `POST /close`.

## Pièges réseau / sandbox / chemins (vue détaillée)

### Piège 1 — Le serveur TextCraft est sensible au cwd

Cause : dans `AgentGym/agentenv-textcraft/agentenv_textcraft/env_wrapper.py`,
`TextCraft_Wrapper.__init__` a `minecraft_dir="agentenv_textcraft/"` codé en
chemin **relatif**. Si on lance ailleurs que `AgentGym/agentenv-textcraft/`,
ça crash sur `FileNotFoundError: agentenv_textcraft/recipes/`.

Toujours faire :
```bash
cd <repo>/AgentGym/agentenv-textcraft
conda activate agentenv-textcraft
textcraft --host 127.0.0.1 --port 36005
```

### Piège 2 — Cursor sandbox réseau

Par défaut Cursor exécute les commandes dans un sandbox avec un namespace
réseau séparé. Un serveur lancé dedans écoute sur `127.0.0.1:36005` *à
l'intérieur* du sandbox, mais le port n'est **pas** exposé à l'hôte.

Symptômes :
- `ss -tlnp | grep 36005` ne retourne rien (ou pointe sur `cursorsandbox`).
- `curl http://127.0.0.1:36005/...` répond `Connection refused`.

Solution : lancer tout serveur d'environnement **hors sandbox**. Avec Cursor,
demander `required_permissions: ["all"]` au moment du `Shell` call.

### Piège 3 — DNS HF dans le sandbox

Avec `required_permissions: ["full_network"]`, `huggingface.co` ne se résout
pas dans le sandbox (`Temporary failure in name resolution`). Pour
`huggingface-cli download`, il faut `required_permissions: ["all"]` (sandbox
complètement désactivé), ou exécuter dans un terminal Cursor classique.

### Piège 4 — Chargement de `agentenv` lent

L'import `from agentenv.envs import TextCraftEnvClient` charge tout
l'écosystème verl + torch + ray (~8 min à froid, mesuré). Le serveur HTTP
lui-même répond en ms. À creuser plus tard pour un dev loop rapide
(probablement réécrire un wrapper minimaliste sans tirer verl).

## Le piège qui nous a pris 1 h : `verl.third_party.vllm` en single-GPU

### Symptôme

`bash examples/eval/textcraft_eval.local.sh` (notre version patchée) :
```
[ActorRolloutRefWorker] NCCL version 2.20.5+cuda12.4
[raylet] A worker died ... Worker exit type: SYSTEM_ERROR
ray.exceptions.ActorDiedError: The actor died unexpectedly.
```

Pas de stack trace côté Python. RAM libre, GPU libre, pas d'OOM kernel
(`dmesg` propre). Crash juste après l'init NCCL → SIGSEGV silencieux dans
le code natif.

### Diagnostic

Étape 1 : on a vérifié les ressources système (OK).

Étape 2 : on a creusé le code. La config par défaut
(`AgentGym-RL/verl/agent_trainer/config/generation.yaml`) contient :
```yaml
load_format: dummy_dtensor
```

`dummy_dtensor` n'est **pas** une valeur de `load_format` standard de vLLM.
La doc vLLM (dans `verl/third_party/vllm/vllm_v_0_6_3/config.py`) liste :
`auto`, `pt`, `safetensors`, `npcache`, `dummy`. `dummy_dtensor` est un
format *custom* ajouté par verl pour le flow PPO multi-GPU :

1. vLLM init avec des poids random.
2. verl patche les vrais poids depuis un **DTensor FSDP** (sortie du training).

Pour notre cas (modèle HF brut, 1 A100), il n'y a aucun DTensor, et l'init
NCCL crash sur des tenseurs invalides.

### Tentatives de fix

| Tentative | Résultat |
|-----------|----------|
| `rollout.load_format=safetensors` (override Hydra) | Même crash NCCL |
| Désactiver custom all-reduce / forcer 1 GPU | Pas testé (déjà single-GPU et ça crash) |
| Test isolant : vLLM **standard** (pip) sur le même modèle | ✅ Fonctionne, génère sans souci |

Conclusion : le **fork** verl de vLLM (`verl.third_party.vllm`) est inutilisable
en single-GPU pour de l'éval avec un modèle HF brut. Il est conçu pour le flow
training PPO multi-GPU exclusivement.

### Décision : workaround par script standalone

Au lieu de patcher le fork verl (1-3 h de debug dans du code natif), on a
écrit un script d'éval direct (`scratch/03_eval_qwen.py`) qui :
- Charge Qwen-3B avec **vLLM standard** (l'install pip).
- Utilise `agentenv.TextCraftEnvClient` (intact) pour parler au serveur.
- Implémente la boucle de rollout multi-tour à la main avec
  `tokenizer.apply_chat_template` + `llm.generate()`.
- Logue chaque trajectoire complète dans `scratch/eval_logs/<item_id>.json`.

Bénéfices secondaires :
- Plus simple à instrumenter pour debug (on contrôle chaque tour).
- Réutilisable comme baseline pour les expériences futures.
- Plus rapide à lire : ~150 lignes vs des centaines dans `main_generation.py`.

Inconvénient : on ne suit plus le flow officiel verl. À documenter clairement
si on revient un jour à `main_generation.py`.

L'eval a été interrompu à 27/100 parce que la VM Spot avait déjà préempté

et tout refaire (les rewards stochastiques avec `temperature=1.0` peuvent
changer), soit (b) ajouter un check `if log existe, skip` dans le script.

Le résultat partiel **Pass@1 ≈ 44 %** est dans la fourchette attendue par
le papier (30-50 % pour Qwen-3B base sur TextCraft selon les sous-tâches).
C'est notre baseline avant tout training RL.

### Observations qualitatives — pourquoi le RL est utile

En regardant les transcripts (`scratch/eval_logs/textcraft_*.json`) :

**Quand Qwen réussit** (2-6 tours) : raisonnement clair "I need X to craft
Y → get X → craft Y". Format respecté (un seul `Action:` par réponse).

**Quand Qwen échoue** (timeout 30 tours), 2 modes pathologiques :

1. **Format violation** : Qwen enchaîne plusieurs `Action:` dans la même
   réponse :
   ```
   Action: get 1 carrot
   Action: craft 1 golden carrot ...
   Action: get 8 gold nugget
   Action: craft 1 gold ingot ...
   ```
   L'env rejette (`Error: Only one 'Action' is allowed per response.`),
   mais Qwen **ne corrige pas son comportement** et boucle 30 fois.

2. **Erreur de planification** : il croit qu'il faut craft un sub-item
   intermédiaire (ex : "il faut craft un golden carrot pour récupérer les
   gold nuggets") alors que `get gold nugget` marche directement.

C'est exactement le terrain où le **RL multi-tour** aide : un signal de
reward au bout de N tours peut apprendre à Qwen à respecter le format et
à mieux planifier (au lieu de re-générer la même mauvaise stratégie).
